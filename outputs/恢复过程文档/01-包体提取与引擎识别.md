# 01：从 MuMu 提取 APK 并识别运行技术

## 目标与原理

先确认安装的具体应用，再从模拟器复制安装包。应用的显示名称、包名、Android版本号、Unity内部版本不是同一概念。不能仅根据名称猜引擎，也不能先假定它属于用户已有Unity工程。

ADB是与Android设备通信的工具；`pm path`返回已安装APK的位置，`adb pull`只把该文件复制到电脑。整个步骤没有修改应用或存档。

## 本次实际环境

- MuMu ADB：`C:\Program Files\Netease\MuMu\nx_main\adb.exe`。
- MuMu实例ADB转发端口：`127.0.0.1:16384`，来源是该实例的vm_config.json。
- 目标显示名称：占城大师。
- 包名：`com.tfzzd.lcsq`。
- Android版本：`versionName=1.04`，`versionCode=104`。
- APK：253,246,448字节，1,919个ZIP条目。
- SHA256：`4544b6323c6a2b11dd801fb75d99dbe6fc59253443bde5a24738d772694b0a2d`。

## 复现步骤

PowerShell中使用完整路径调用ADB：

```powershell
$adb = 'C:\Program Files\Netease\MuMu\nx_main\adb.exe'
& $adb connect 127.0.0.1:16384
& $adb -s 127.0.0.1:16384 shell pm list packages -3 -f
& $adb -s 127.0.0.1:16384 shell pm path com.tfzzd.lcsq
& $adb -s 127.0.0.1:16384 shell dumpsys package com.tfzzd.lcsq
```

显示名称是通过MuMu自身CLI核对的：

```powershell
& 'C:\Program Files\Netease\MuMu\nx_main\mumu-cli.exe' control -v 0 app info --installed
```

`pm path`输出的安装目录包含随机段，重新安装后会改变，应每次重新读取。然后将该输出中的完整APK路径传给`adb pull`，不要把本次随机路径当作通用路径。

```powershell
# 把下列两个变量分别设为本次 pm path 的输出和你自己的目标文件。
# $deviceApk = '/data/app/.../base.apk'
# $localApk = 'D:\Research\占城大师.apk'
& $adb -s 127.0.0.1:16384 pull $deviceApk $localApk
Get-FileHash -LiteralPath $localApk -Algorithm SHA256
```

本次正式副本在上级输出目录的`占城大师-1.04.apk`，工作副本另放work/apk-intake。

## 如何确认Unity与IL2CPP

APK可按ZIP读取。发现如下文件才形成实际证据：

- `lib/arm64-v8a/libunity.so`与`libil2cpp.so`。
- `lib/armeabi-v7a/libil2cpp.so`，说明同时含ARMv7实现。
- `assets/bin/Data/Managed/Metadata/global-metadata.dat`。
- `assets/bin/Data/data.unity3d`。
- `assets/aa/settings.json`和`catalog.bundle`，说明使用Addressables资源。

UnityFS头记录Unity `2022.3.62f3`；Addressables设置记录`1.22.3`。Android版本1.04与后续读到Unity PlayerSettings的2.17.1是两个元数据口径，应分别记录，不应互相覆盖。

## 本次排除的误区

最开始安装列表中还有`com.cl.HexGame`和用户自己的AutoChess，均不能因为名字像Unity游戏就当作目标。先使用应用显示名称与包名对应，才提取正式目标。

本步骤的成功只表示拿到了正确APK并识别技术栈；没有恢复源工程，也没有运行Windows版游戏。
