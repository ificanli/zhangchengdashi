# 04｜资源工程导出与字段恢复

这一步把 APK 中的真实场景、Prefab、贴图、动画和序列化脚本字段恢复成 Unity 工程文件。交付工程是 `outputs/OccupyCityRecovered`。**完成这一阶段不等于恢复了原游戏的 C# 方法，也不等于已经能够运行原玩法。**

本文面向希望学习实际恢复过程的开发者。它记录采用的方法、验证证据和失败边界，避免把“导出成功”“字段可读”“Unity 能编译”“原玩法可运行”混成同一个结论。

## 1. 本阶段的输入

| 输入 | 用途 |
|---|---|
| `work/apk-intake/zhancheng-dashi-1.04.apk` | 原始包体，保持原件不变 |
| `work/metadata-probe/global-metadata.decoded.dat` | 前一阶段恢复的 IL2CPP 类型 metadata |
| `work/il2cpp-dump-decoded/DummyDll` | 118 个类型声明程序集，为自定义 MonoBehaviour 提供字段布局 |
| `work/asset-probe/.venv` | 已隔离安装 UnityPy 1.25.4 的 Python 环境 |

APK 的 SHA-256：

```text
4544b6323c6a2b11dd801fb75d99dbe6fc59253443bde5a24738d772694b0a2d
```

先把 APK 解压到 `work/recovery-input`，共 1,919 项、534,330,959 字节。对每个 ZIP 条目先验证目标绝对路径位于解压目录下，再解压。然后只将工作副本中的 `assets/bin/Data/Managed/Metadata/global-metadata.dat` 替换为已解码文件。

原始 APK 没有修改，前后 metadata 哈希保存在 [input-provenance.json](证据/资源导出/input-provenance.json)。

## 2. 工具版本与调用方式

使用 [AssetRipper 官方 2.0.0 发行版](https://github.com/AssetRipper/AssetRipper/releases/tag/2.0.0)，文件为 `AssetRipper_win_x64.zip`。下载体积 44,439,367 字节，SHA-256：

```text
9a7ef0e7c5c3ea5b90b4e6d855e2d98d5f7ec8c3f9e26fccbc194c6a7b01baf7
```

工具本身报告 2.0.0.0，Release Published，编译时间为 2026-08-24 18:48:30 UTC。官方源代码也下载到工作目录，专门核对了平台检测、程序集导入和导出行为，没有修改工具。

本次通过本地 headless HTTP 服务使用工具。等效启动参数为：

```powershell
AssetRipper.GUI.Free.exe --headless --port 57631 --log-path <工作目录中的日志路径>
```

服务仅监听 `127.0.0.1`。先读取 `/openapi.json` 确认接口定义，再读取 `/Settings/Edit` 和官方源码核对字段含义。主要接口：

| 请求 | 用途 |
|---|---|
| `POST /Settings/Update` | 设置默认 Unity 版本、脚本/贴图/Shader 导出模式 |
| `POST /LoadFolder`，多个 `Path=` 表单项 | 一次加载原资产、DummyDll 和正常化的旧资源包 |
| `POST /Export/UnityProject`，`Path=` | 导出独立 Unity 工程 |

脚本设置为 `Decompiled`、C# 9；资源按原路径 DirectExport；Sprite 使用 YAML 保留完整元数据；保留不可读资产。免费版的 Shader 设置为 Dummy，这个限制没有隐瞒。

导出接口会在 headless 模式删除非空目标目录，因此每次都使用新的工作目录；首次导出作为对照保留，最终导出完成后才把 `ExportedProject` 移动到交付目录。

## 3. 为什么把 DummyDll 作为独立输入

主数据包没有保留完整类型树。最初 UnityPy 能读到脚本身份和 MonoBehaviour 通用头，但大量自定义字段无法正确消费。这时只导出 GameObject 和贴图会得到一个缺乏真实脚本字段的工程。

AssetRipper 官方 `MixedGameStructure` 在输入目录中发现托管程序集时选择 `MonoManager`，用程序集里的类型/字段定义解释序列化数据。本次因此传入三个独立路径：

```text
work/recovery-input/assets
work/il2cpp-dump-decoded/DummyDll
work/recovery-normalized/legacy-bundles
```

日志显示发现 118 个程序集。**这里的 Mono 是工具的字段解析路径；原 APK 仍然是 IL2CPP。** DummyDll 中的方法为空或返回默认值。导出的 7,560 个 C# 文件不是 7,560 份原始源码，也没有恢复原玩法算法。

能确认恢复的是具体字段。例如启动场景中的 `GameStartEntry` 恢复出 `AppName=ljzs_lt`、`gameCode=U-CSZDZ`、语言选项及 fastmode 配置。字段来自原包的序列化载荷，不是手工给组件填默认值。

## 4. 找到被工具跳过的 16 字节资源包前缀

第一次导入只识别到 Addressables 的 19 个 Android bundle、catalog 和 `data.unity3d`。追踪启动链后，发现 `assets/Android/ljzs_lt` 还有旧框架资源。

读取二进制头发现，30 个 `.unity3d` 和 manifest 的 `UnityFS` 签名都位于 **offset 16**：

```text
[16 字节包头] 55 6E 69 74 79 46 53 00 ...
              U  n  i  t  y  F  S
```

AssetRipper 的目录扫描按文件起始签名判断是否为 bundle，因此会跳过这些文件。修复方法是生成新的派生文件，精确去掉头部 16 字节，不修改 APK 解压原件。31 个派生文件逐一交给 UnityPy，全部成功读取；文件哈希和对象数记录于 [legacy-bundle-normalization.json](证据/资源导出/legacy-bundle-normalization.json)。

随后将这些派生文件和主包一起重新导出，保证跨包引用由同一次导出生成，不手工拼接两套不同 GUID 的项目。旧包还带来了 `MineGameTest` 场景。

仍未处理的旧内容是两个不含明文 UnityFS 签名的 `.unity3d`，以及 `ABFiles.txt`。它们被列为明确缺口，没有假设不存在或已解码。

## 5. RedDotData：恢复递归字段而不是忽略错误

AssetRipper 报告 `RedDotData` 布局不匹配：读了 24 字节，预期 3,116 字节。该资源在 `resources.assets` 的 PathID 为 3189，原始对象共 3,160 字节，头部 44 字节，字段载荷 3,116 字节。

恢复出的声明明确给出了数据结构：

```csharp
[Serializable]
public class RedDotNode {
    public string name;
    public string redDotClassName;
    public string collectionClassName;
    public string varKey;
    public string comment;
    public RedDotNode[] children;
    [NonSerialized] public bool isExpanded;
}
```

按 Unity 的长度前缀 UTF-8 字符串、4 字节对齐、数组计数和递归子节点规则解析；`isExpanded` 因 `[NonSerialized]` 不读取。成功得到 56 个节点，恰好消费全部载荷。

为了确认不是“看起来读通”，把解析后的树按同一规则重新编码，结果与原始 3,116 字节**逐字节完全相同**。随后才向导出的 `RedDotData.asset` 写入 `rootNode`。这修复的是原始数据，没有填造节点或补造业务方法。

相关证据包括原始 bytes、解出的 JSON、修复前 YAML 和 [post-export-repairs.json](证据/资源导出/post-export-repairs.json)。

## 6. 修复主场景的四处旧 GUID 引用

主数据与旧框架包存在同路径场景内容。最后写出的主场景 `.meta` GUID 为：

```text
85e9211fb5d03f24ab458af25e284f9f
```

四处引用仍使用先前生成的 `3bff343352a5e094db6792d5e814b029`。核对实际场景、文件 ID 和 meta 后，只修复了：

1. `ProjectSettings/EditorBuildSettings.asset`；同时对齐实际路径大小写。
2. 主场景的 `LightingData.asset`。
3. 两个从原场景导出的本地化目标 ScriptableObject。

没有批量改写所有 GUID，也没有将不存在的类绑定到类似名称的脚本。

## 8. 这一步之后还欠什么

工程结构和真实字段已经可供后续恢复，但本阶段没有启动 Unity、没有编译、没有进行游戏画面或玩法验收。150 个 Shader 仍是占位 Shader；导出的包代码和业务代码仍包含 DummyDll 的默认方法体；依赖清单尚未恢复完整；两个旧资源包及 ABFiles 仍未解码。

后续真实包替换和 GUID 迁移见 [06｜真实依赖与脚本引用修复](06-真实依赖与脚本引用修复.md)。运行目标仍然是原游戏逻辑，不能通过删除启动逻辑或另造简化玩法把“能够打开工程”当成完成。
