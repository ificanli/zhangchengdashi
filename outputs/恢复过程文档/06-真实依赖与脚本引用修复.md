# 06｜真实依赖与脚本引用修复

资源导出的 C# 类型外形可以帮助读取字段，但默认方法体不能提供原来的运行行为。本阶段把已能从官方来源取得的 Unity 包、UniTask 和 Newtonsoft 恢复为真实实现，并把场景、Prefab、ScriptableObject 的脚本引用迁移到真实包的 `.meta` GUID。

本阶段没有恢复业务方法。第一批恢复Unity包，第二批已恢复LitJson、MemoryPack历史Unity版与Spine4.2；DOTween Pro、A*、GPU Instancer等仍需另外确认来源与实现。Unity 的统一导入和编译由主流程执行；本文记录依赖修改本身以及静态读回结果。

## 1. 为什么不能直接删除导出的包脚本

Unity 的 `MonoBehaviour.m_Script` 存的是脚本 GUID 与 fileID，而不只是 C# 类名。例如场景中的 UI Text 即使名字仍叫 `UnityEngine.UI.Text`，从导出的脚本换成官方 UGUI 后，两个 `.meta` GUID 也会不同。

如果只移走 stub，再装包，已有组件会变成 Missing Script。因此替换顺序是：

1. 从 stub 提取原程序集、命名空间、类型名和旧 GUID。
2. 从目标官方包提取同一身份的真实脚本和 GUID。
3. 对所有有序列化实例的类型确认唯一目标。
4. 备份并迁移资产里的旧 GUID。
5. 移出原 stub，加入真实包，随后由统一 Unity 进程导入验证。

本次实际移出与写入顺序在一次受控操作中完成，期间未运行 Unity。原文件全部保留在 `work/recovery-stubs`，没有删除原件。

## 2. 版本证据的强弱

`Properties/AssemblyInfo.cs` 只给出 CLR 程序集版本。大多数 Unity 包是 `0.0.0.0`，这并不能证明原项目用了哪个 UPM patch。Newtonsoft 的 `13.0.0.0` 也不能直接区分 13.0.1、13.0.2 等产品版本。

本次先读导出的声明，再核对两类本地官方来源：

- Unity `2022.3.62f3c1/Editor/Data/Resources/PackageManager` 自带的 BuiltInPackages 和 Editor `.tgz`。
- `AppData/Local/Unity/cache/packages/packages.unity.cn` 中已有的官方包。

Addressables 1.22.3 有包内版本证据，且编辑器内带同版本；URP/TMP 等选用该 2022.3 编辑器随附版本。Entities 等以已缓存且支持 Unity 2022.3 的版本作为可验证兼容候选。不能把后两类写成“已精确找回原项目版本”。

## 5. GUID 匹配与 partial class 的陷阱

匹配键采用：

```text
程序集名称 + 命名空间 + 声明类型名
```

目标程序集从最近的官方 `.asmdef` 取得，不依赖文件夹名称猜测。目标 GUID 从官方脚本的 `.meta` 读取。不能只按文件名或短类名匹配，因为不同程序集可以存在同名类型。

还遇到了实际的多候选情况：TextMeshPro、TextMeshProUGUI、URP 的 Bloom、UniversalRenderPipelineAsset 等使用 partial class。官方主脚本与辅助文件都声明同一类型，但只有主脚本才应该成为序列化组件指向的 MonoScript。例如不能把 TextMeshProUGUI 指向 `TMPro_UGUI_Private.cs`。

处理方式：先核对完整类型身份，再在同身份的多候选中选择与类型名一致的主脚本文件。若仍然不唯一，就停止该类型迁移，不进行模糊选择。

最终建立 2,433 条旧→新 GUID 映射。有 553 个非实例化/辅助类型没有唯一源文件映射；它们中没有一个是本轮被移出程序集里、实际序列化组件正在引用的类型。这些项保留在计划清单里，不把“无序列化实例”当成 API 兼容保证。

所有被替换程序集的已有序列化组件都匹配到了真实目标，待匹配组件为 **0**。

## 7. 本轮没有乱换的第三方内容

- **Spine**：115 份 JSON 骨骼数据都声明 `4.2.43`，另外两份 `.skel.bytes` 的头部也包含 `4.2.43`，因此恢复时应以官方 spine-runtimes 4.2 系列为候选，并按相应 Spine Runtime 许可与用户已有授权处理。`4.2.43` 是资产导出版本，不直接等于 runtime Git commit。本轮没有下载破解版本，也没有先拿不同主版本来凑编译。
- **DOTween / DOTween Pro**：AssemblyVersion 都是 1.0.0.0，真实产品版本存在静态字段，其初始值没有从 DummyDll 恢复。免费 DOTween 应取 Demigiant 官方来源；DOTween Pro 应使用官方授权包，不能把免费版当成 Pro 的等价替代。
- **A* Pathfinding / ALINE Drawing、GPU Instancer、Mesh Baker、Odin、All In 1 VFX 等**：需要对应原库版本和正式来源。本轮保留原恢复声明，不将另一个商业版本强行装入。
- **其他代码库**：LitJson、NCalc、MemoryPack、Clipper、UIParticle 等仍需逐项追踪 API/版本。本轮没有给它们添加伪实现来掩盖缺失。

## 8. 如何理解本阶段的通过与未通过

已经通过的是：官方包来源核对、明确版本选择、stub 安全归档、序列化脚本身份匹配、GUID 改写的静态读回。

尚不能据此宣称：Unity 已经成功解析所有包、全部脚本已经编译、第三方库已经恢复、Shader 视觉已经正确，或原游戏玩法已经运行。后续 Unity 导入日志和原方法恢复会继续给出独立结论。包版本候选如果暴露 API 差异，应依据实际错误回到版本证据修正，不删除调用来制造编译通过。


## 9. 第二轮 Unity 编译后：选择下一批真实运行库

主流程的第二轮 Unity 导入已经解决第一轮程序集循环引用，进入实际 C# 编译。本阶段读取其日志，将重复输出去重后得到 500 条唯一编译错误。出现最多的是商业 MeshBaker 126 条和 GPU Instancer 85 条；可公开取源候选中，MeshSimplifier 81 条、LitJson 64 条、MemoryPack 22 条、spine-csharp 9 条。

错误样式大量为 `CS0535` / `CS0738` / `CS0737`：接口未实现、枚举器返回类型不对、状态机方法访问级别不对。检查导出代码可见，这来自 DummyDll 的反编译声明失真。逐条补空接口虽然可能减少编译错误，却无法恢复原行为，因此本批继续换回真实官方源码。

### 一个需要拒绝的“同名替换”

起初按错误数量检查了 `Whinarn.UnityMeshSimplifier.Runtime`，但原包的实际命名空间是：

```text
BrainFailProductions.PolyFew.UnityMeshSimplifier
```

原声明还包含 `toleranceSpheres` 等 PolyFew 扩展。Whinarn 官方 MIT 上游 3.1.1 使用 `UnityMeshSimplifier` 命名空间，不能仅因为程序集名称相同就把它当成原实现。**因此没有替换这 81 条错误对应的库，也没有通过改名伪造 PolyFew。** 官方源码只保留在工作目录用于对照。

本批最终选择 LitJson、MemoryPack 历史 Unity 版、Spine 4.2。System.Runtime.CompilerServices.Unsafe 是 MemoryPack 的实际运行依赖，同批恢复。

## 10. MemoryPack：从 API 形状定位到历史官方版本

最新 MemoryPack 1.21.4 的 Writer API 与原包不相同。原包程序集名为 `MemoryPack.Core2021`，使用非泛型的 `MemoryPackWriter`，Formatter 接口形状是：

```csharp
void Serialize(ref MemoryPackWriter writer, ref object value);
void Deserialize(ref MemoryPackReader reader, ref object value);
```

检查官方历史 tag 后，选用 [MemoryPack 1.9.16](https://github.com/Cysharp/MemoryPack/releases/tag/1.9.16) 的 **Unity 专用完整源码**。其 package.json 要求 Unity 2021.3，Writer、Formatter、SerializerOptions.ServiceProvider 等 API 与原声明一致。本次没有安装不匹配的最新版本。

实际嵌入包为 `Packages/com.cysharp.memorypack`。只将官方 asmdef 的程序集名从 `MemoryPack` 保持为原项目需要的 `MemoryPack.Core2021`，以保留现有 GFRunning 程序集引用；没有修改序列化算法或填造方法。

同一官方仓库附带的 `System.Runtime.CompilerServices.Unsafe.dll` 为强命名程序集 6.0.0.0，与原声明一致。将其作为真实 DLL 加入，归档原来的 Unsafe stub。相关 LICENSE 保留。实件 SHA-256：

```text
01748200f2400c742aa689f1f5101bd6298efdfd92c00c18f4fa473847235ba9
```

官方 MemoryPack Roslyn 生成器暂未激活。原因是恢复出的业务类带有 `MemoryPackable` 标记，同时保留 IL2CPP 导出的生成方法，而且类声明尚未恢复成 partial。直接运行生成器会与现有声明冲突。生成器原件完整保存在官方源码工作目录，业务恢复阶段负责移除已失真的生成声明并启用真正生成。**恢复核心库不等于已经恢复业务数据 formatter。**

## 11. LitJson：恢复真实 JSON 解析与序列化

采用 [LitJSON 官方 0.19.0](https://github.com/LitJSON/litjson/releases/tag/0.19.0)。源码包含原包调用的 `ToJson`、泛型与非泛型 `ToObject`、`ToObject(string, Type)`、Exporter/Importer 注册等 API。

上游是普通 C# 库，不自带 Unity asmdef。因此把其 10 个 `.cs` 源文件原样复制到 `Assets/RecoveredLibraries/LitJson`，添加名为 `LitJson` 的程序集定义，并保留官方 `COPYING`/Unlicense 文本。解析器、Lexer、JsonData 的实现都来自官方源，没有写替代解析器。

迁移前扫描确认，LitJson、MemoryPack、Unsafe 的旧脚本 GUID 没有被任何序列化资产引用，因此这三项不需要把组件指向新脚本。

## 15. DOTween：保留真实官方源码、原程序集和设置资产身份

恢复采用官方提交：

```text
bfb02b05551a45204352dc43bdc15b882147891a
```

该提交 `DOTween.Version` 为 **1.3.045**。原 APK 的静态版本字符串没有从 DummyDll 初始化体中恢复，因此这里明确属于官方兼容候选，不声称已证明是原 APK 的精确产品版本。

将官方 `_DOTween.Assembly/DOTween` 下 104 个 C# 文件原样放入 `Assets/RecoveredLibraries/DOTween`，保留程序集名 `DOTween`，因此现有 GFRunning、GFHanldMono、DOTweenPro 的程序集引用无须改名。`DOTweenSettings` 的 27 个现有顶层字段在官方源码中全部存在，其资产 GUID 保持：

```text
5cbd73210618a4aa2c3963be80651995
```

官方源码不提供对应 Unity meta 时，不能随意生成新 GUID 丢掉设置引用。本次按程序集、命名空间和类型名精确匹配，把导出脚本 meta 保留到对应真实源文件。

读回审计还发现：95 个匹配类型实际分布在 **92 个**官方 `.cs` 文件中。`CircleOptions`、`StringPluginExtensions`、`OrientType` 与主类型共处一个文件，不能让辅助类型的 meta 覆盖主文件 meta。修正后只保留92个主文件meta；三个无序列化实例的辅助类型旧meta身份单独记录。这是“类型数量不等于MonoScript文件数量”的实例。

**免费模块仍需单独恢复。** 七个 `DOTweenModule*` stub 实际位于 `GFRunning/DG/Tweening`，由业务恢复流程拥有。本批没有跨边界改写它们。相同官方提交的对应模块源码已经备好，在工作目录的 `_DOTween.Assembly/bin/Modules`。核心真实运行并不自动让这些旧模块有真实逻辑；DOTween Pro 也仍未恢复。

## 16. UIParticle：为何选3.3.14而非最新4.x

最新官方4.14.1不再暴露原组件的一些成员。现有60个组件序列化了 `m_IsTrail`、`m_IgnoreCanvasScaler`、`m_Scale`、`m_Scale3D`、`m_AnimatableProperties`、`m_Particles`、`m_ShrinkByMaterial`，原代码还使用 `activeMeshIndices` 等属性。

官方 **3.3.14** 的字段和API形状与这些证据一致，因此把该固定tag作为嵌入包 `Packages/com.coffee.ui-particle`，保留MIT LICENSE和官方meta。runtime/editor程序集定义只增加Unity2022.3需要的显式UGUI引用，未改粒子渲染代码。

60个组件的脚本GUID全部迁移到官方UIParticle脚本，共涉及10个序列化文件。字段值保持原样，没有因为新版本默认值而重建组件。

## 17. NCalc：精确1.3.8版本的实际求值验证

原恢复程序集的版本是1.3.8.0。通过NuGet官方包源取得作者Sebastien Ros的 `ncalc/1.3.8`，包内的强命名程序集为：

```text
NCalc, Version=1.3.8.0, Culture=neutral, PublicKeyToken=973cde3f1cafed03
```

原样DLL放入 `Assets/Plugins/RecoveredNCalc`，原stub归档；包已包含所需Antlr类型，未拿新的NCalc主版本替代旧接口。原nuspec一并保留，它指向历史CodePlex许可页；本报告没有在无法核实旧链接全文时替它宣称一个新的许可证。

NCalc没有Unity序列化脚本引用，因此无需组件GUID迁移。为了确认装入的不是另一个空壳，直接加载这份官方DLL运行两个小检查：

```text
1 + 2 * 3           → 7
[x] * 2，参数x=7   → 14
```

两项通过。这是实际数学求值，不是只检查文件存在；也不代表游戏中所有表达式都已验收。DLL SHA-256：


## 18. 明确保留的差异与第三批读回

恢复出的BurstTriangulator具有 `ConstraintType`、`ConstraintEdgeTypes`、`HalfedgeState`，其中还区分 `ConstrainedAndHoleBoundary`。检查的官方3.0.0和3.9.2源码没有这组形状，不能把这些边界约束直接当布尔值替换。可能存在历史分支或项目修改，目前证据不足以选定等价官方源，故保留原恢复声明，没有强行升级。

第三批静态验收结果：

- 3个stub目录安全归档，未删除原件。
- DOTween104个C#文件、UIParticle16个代码/Shader文件与固定官方源逐字节相同。
- 92个DOTween主文件meta身份保留正确，设置资产的实际引用未变。

- Spine/MemoryPack未被本批修改；商业库和业务方法未被本批改写。
