## 1. 这一阶段要解决的问题

Il2CppDumper 导出的 DummyDLL 能提供类名、字段、签名和原生地址，但通常没有原方法体。把它们导入 Unity 不等于恢复游戏。

本阶段验证 Cpp2IL 是否能沿以下链路恢复真正可执行的方法：

```text
APK 原生 ARM64 方法字节
  → Cpp2IL 平台指令分析
  → ISIL 中间表示与控制流
  → CIL 方法体
  → 写入托管 DLL
  → CLR 直接调用
  → 与原始 ARM64 方法逐输入对照
```

限定恢复两个方法，避免直接分析全游戏导致结果暴涨、难以辨别真伪：

| 方法 | 原生地址 | 原生字节范围 | 当前结论 |
|---|---:|---:|---|
| `HexManager.HexDistance` | `0x3D2A600` | 160 字节 | 已修复值类型 ABI、位宽和条件标志，真实 DLL 与原生 1137/1137 一致 |
| `GameModule.SynergyEffectManager.InternalCalculateDamage` | `0x3E0F6F0` | 56 字节 | 修复工具后生成真实 CIL，直接调用通过，556 组原生对照全部通过 |

**试验用 Assembly-CSharp.dll 中仅选中的方法参与真实恢复，其他方法被显式设置为 throw。它是可检查的实验载体，不能作为完整游戏 DLL 交付或宣称已恢复游戏。**

## 4. 原样运行为何失败

### 4.1 HexDistance：有 IL 不等于有效 IL

官方开发版为 HexDistance 输出了 118 条 CIL，ILSpy 却出现：

```text
Expected Obj, but got VT
Unknown result type
Unsupported input type for neg
```

对应 C# 含有 `object obj = a >> 32;`、对 `object` 做加减、直接比较两个 `HexCoord` 等表达式。将原样反编译成员放进有真实 `q/r` 字段的最小宿主后，编译报 **18 个错误**。

元数据表明 `HexCoord` 的 `q`、`r` 是两个 32 位字段，偏移分别为 0 和 4。ARM64 ABI 把这个 8 字节值类型打包在一个 X 寄存器，`LSR X21, X0, #32` 取高 32 位。Cpp2IL 当前把 X0 直接等同于托管 `HexCoord`，却没有把高低位恢复成字段读取。

### 4.2 伤害方法：C# 看起来合理仍可能出错

官方原样输出 39 条 CIL。直接反射调用该 DLL 的真实方法，抛出：

```text
System.InvalidProgramException: Common Language Runtime detected an invalid program.
at GameModule.SynergyEffectManager.InternalCalculateDamage(...)
```

ILSpy 可以给出能编译的 C#，但有类型警告，并把核心逻辑错误地提升成 double 运算。它甚至把 `0x7F800000` 浮点位模式当作整数 `2139095040` 比较。

精度反例：`originalAttack=16777219`、`fetterCount=4`、`requiredCount=4`。

| 路径 | 结果 |
|---|---:|
| 原生 ARM64 | 25165829 |
| 原样 Cpp2IL 反编译 C# | 25165828 |

这说明“能反编译”“能重新编译”和“语义与原生一致”必须分别检查。

## 5. 原生方法到底做了什么

原生 56 字节方法没有调用其他方法，适合建立独立机器码 oracle。关键指令为：

```asm
CMP W3, W4
MOV W0, W1
B.LT return
SCVTF S0, W0
FMOV S1, 0.5
FMUL S0, S0, S1
FMOV S1, W8        ; W8 的位模式是 0x7F800000，即 float 正无穷
FCVTZS W8, S0
FCMP S0, S1
CSEL W8, W9, W8, EQ
ADD W0, W8, W0
RET
```

`SCVTF S0,W0` 必须先转换为 **float32**，`FCVTZS` 必须执行截断转整数，`FMOV S1,W8` 是位模式重解释；这三件事不能都简化成 Move。

`isEnemy` 参数在该原生方法中未参与计算；测试仍覆盖 true/false，以确认这不是工具误删分支。

## 6. 工具代码修复

最初的标量恢复更改以下 6 个 Cpp2IL 源文件；后续 HexDistance 修复还更改 `Analysis/FlagConditionRecovery.cs`。完整当前差异见证据目录 `cpp2il-tool-fix.diff`：

| 文件 | 修改目的 |
|---|---|
| `Cpp2IL.Core/ISIL/OpCode.cs` | 增加带明确源类型和目标类型的 `Convert`、`Bitcast` |
| `Cpp2IL.Core/ISIL/Instruction.cs` | 声明转换操作的定义/使用关系，供 SSA 正确追踪 |
| `Cpp2IL.Core/Analysis/DeadCodeEliminator.cs` | 允许删除未使用的纯转换操作 |
| `Cpp2IL.Core/Analysis/LocalVariables.cs` | 依据转换指令确定输出类型，避免误传播为 object/double |
| `Cpp2IL.Core/InstructionSets/NewArmV8InstructionSet.cs` | 保留 SCVTF、FCVTZS 和寄存器 FMOV 的真实语义；S 寄存器立即数采用 FloatLiteral |
| `Cpp2IL.Core/IlGenerator.cs` | 生成正确转换、位重解释、整数常量宽度和可验证的方法体 |

修复分为四部分：

1. **数值转换**：SCVTF、FCVTZS 不再落成普通 Move。根据 W/X/S/D 寄存器选择 Int32/Int64/Single/Double，并生成 `conv.i4`、`conv.i8`、`conv.r4`、`conv.r8`。
2. **位重解释**：整数与浮点寄存器之间的 FMOV 使用 `BitConverter.Int32BitsToSingle` 等对应操作。立即数 `0.5` 写入 S 寄存器时保持 float32。
3. **方法体验证**：原输出 `.maxstack 0`，改为实际计算最大栈深度；原实现把诊断 call 追加在最终终止块之后，形成没有 ret/throw 的尾段，改成写日志，避免污染真实方法逻辑。
4. **FCVTZS 完整边界**：ARM 浮点转有符号整数会饱和，NaN 转 0。直接使用 CLR `conv.i4/conv.i8` 的超范围行为可能随运行时变化，因此在 CIL 内显式处理 NaN、上下界，再对范围内数值截断。

这些规则以指令和数据类型为依据，**没有根据方法名匹配目标伤害公式**。

## 8. 仍未恢复的点和下一步

**最新两个指定目标方法的自动可执行覆盖为 2/2，不是整个 Assembly-CSharp 的成功率。** 伤害方法通过 556 项、HexDistance 通过 1137 项直接 DLL 与原生机器码对照。下面保留的 ABI 问题清单是本阶段实际修复所依据的问题；泛化范围见第 10、11 节。

HexDistance 需要进一步补足：

1. AAPCS64 小值类型的参数打包/拆包。当前调用约定解析器对每个非浮点参数只分一个整数寄存器，没有恢复值类型字段布局。
2. W/X 寄存器的位宽和截断。当前归一化把 Wn 和 Xn 合并为同一个寄存器名；若仅把 struct 强转成 long，低 32 位计算和符号仍可能错误。
3. ADDS/SUBS 的标志产生顺序。源码目前先写目标，再用源操作数发出比较标志；当源寄存器也是目标寄存器时，SSA 可能读到更新后的值。例如 `SUBS W9,W9,W22`。
4. 对包含上述操作的方法，需要独立原生输入 oracle；必须先有失败反例，再扩大通用修复范围。

ARMv7 不是现成的自动恢复后备方案：当前官方 `ArmV7InstructionSet.GetIsilFromMethod()` 直接 `return []`，只能取得反汇编，不能生成有意义的 ISIL。应先解决 ARM64 真实缺口，不能靠切架构宣称恢复成功。

本次新增转换规则只覆盖带 W/X/S/D 标量寄存器的非定点 SCVTF/FCVTZS；带缩放立即数的定点变体会显式失败，不冒充已正确支持。其他原有浮点转换指令仍可能沿用官方不完整实现，需要按实际方法继续建立对照。52 项独立回归覆盖 CIL 转换/边界发射层；556 项才是本游戏原始机器码到恢复 DLL 的完整方法级对照。

下一阶段建议保留当前已通过的 556 条 oracle，建立 HexCoord 的受控机器码对照，修复值类型 ABI、寄存器宽度和别名标志问题后，再小批量扩大方法范围。主工程仍需资源、原生插件、序列化和启动链的完整恢复与 Unity 验收。

## 11. 100 个真实短方法的泛化验证

为避免只拟合两个函数，本阶段按真实 ARM64 字节长度和指令模式，从 Assembly-CSharp 建立候选池：181 个短 getter、51 个短 setter、7 个无外部调用的短数值/常量方法。固定种子抽出 **46 getter + 47 setter + 7 数值/常量 = 100 方法**。

这不是整个程序集的随机代表样本：它刻意针对最基础、最容易独立验证的恢复层。构造函数和含外部调用的初始化链不在本次 100 个独立方法验收内。

每个方法用 3 组输入，对其原始 ARM64 字节建立 oracle：getter 将字段置为非零/负数/大整数或浮点位模式后读取；setter 检查实际字段写回；数值方法比较返回值的原始位模式。每个托管方法在独立 CLR 进程验证，每进程 25 秒上限、最多并行 4 个，避免单个非法 IL 或类型初始化拖住整批。

第一轮结果：**85 个真实通过**（41 getter、42 setter、2 数值），4 个原生常量返回单列不计，11 个执行环境失败。未观察到数值语义不一致。失败分为：9 个抽象基类不能直接分配实例，2 个类型依赖未恢复的静态构造函数（`BattleGameSceneManager`、`HexBehaviour`）。

第二轮使用 APK 中原有的具体派生类型，分配实例后调用原抽象基类的方法；没有生成假构造函数，也没有跳过静态初始化。结果为 **93 个真实通过**（45 getter、46 setter、2 数值），5 个原生常量返回不计成功，2 个依赖静态初始化仍失败。93 个通过方法各 3 组机器码对照，共 279 项有效方法输入通过。

## 15. 当前边界和可继续的方向
