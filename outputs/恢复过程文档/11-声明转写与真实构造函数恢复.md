# 11：区分声明转写错误与缺失的方法实现

状态：42个文件的显式接口声明已修复，所有原方法/访问器正文保持不变；另从原ARM64恢复10个结构体构造函数并通过44项隔离检查。整体工程仍有其他未恢复方法，正在第四轮Unity导入，尚未证明完整编译或运行。

## 一、显式接口为什么会“看起来存在，却没有实现接口”

原IL中可以用方法实现表将私有方法绑定到接口。DummyDll导出并再反编译成C#后，部分成员名称变成合法的转义标识符，例如：

```csharp
private object System_002ECollections_002EIEnumerator_002ECurrent { get { ... } }
private void System_002EIDisposable_002EDispose() { ... }
```

C#编译器将它们视为普通私有成员，不会自动还原IL的接口映射。因此即使类声明了IEnumerator/IDisposable，仍报CS0535或CS0737。

正确的声明身份应为：

```csharp
object System.Collections.IEnumerator.Current { get { ... } }
void System.IDisposable.Dispose() { ... }
```

这一步只恢复“该成员实现哪一个接口”的声明。原来为空的方法仍为空，不能因为接口编译错误消失，就把它算成方法实现恢复。

## 二、如何约束自动修复范围

使用本机.NET SDK所带Roslyn解析C#语法树，而不是对整文件盲目替换文本。转换器只处理：

- 名称中的`_002E`、`_003C`等编码可准确还原为System接口成员的声明。
- 实际声明了IEnumerator的类型中的私有MoveNext。
- 实际声明了IAsyncStateMachine的类型中的MoveNext和SetStateMachine。
- 生成的独立`get_Current`辅助方法保持原样，访问器中的调用不更名。

每个文件修改前备份，并比较修改前后所有方法和访问器的Body/ExpressionBody序列：必须逐字节相同，否则停止写入。修复后再次解析语法树，不允许引入新的语法错误。

本次修改42个文件，记录位于`证据/声明与构造/declaration-repair.json`。目标只包含本批指定的第三方导出目录，没有批量修改官方已恢复源码或业务方法。

## 三、结构体构造函数不能靠填零来恢复

PolyFew扩展版MeshSimplifier的空构造函数导致CS0171：所有字段必须在返回前赋值。该库与公开Whinarn上游存在扩展差异，不能仅按程序集名称直接替换。

本次实际检查原ARM64构造函数中的STP/STR、浮点转换、条件选择和常量，然后写回同名C#构造：

| 类型 / 构造 | RVA | 从原指令确认的行为 |
|---|---|---|
| BlendShape(string, frames) | 0x854F0B0 | 保存名称和数组引用 |
| BlendShapeFrame(weight, arrays) | 0x854F0B8 | 名称String.Empty、offset=-1、保存权重和数组引用 |
| BlendShapeFrame(name, weight, arrays, offset) | 0x854F13C | 逐字段保存全部实参 |
| BorderVertex(index, hash) | 0x8569100 | 保存两个int32 |
| LODLevel(height, quality) | 0x854F458 | 高度/质量钳0..1，其余使用原默认值 |
| LODLevel五参数 | 0x8555698 | 保存fade/flags，renderers=null |
| LODLevel六参数 | 0x8555634 | 保存renderer引用并写入完整原默认渲染枚举 |
| Vector3d(double) | 0x856D2E8 | 同一值赋给x/y/z |
| Vector3d(x,y,z) | 0x856D2F4 | 保存三个double |
| Vector3d(Vector3) | 0x856D300 | 三个float32分别扩宽成float64 |

LOD构造中只有height和quality被钳制；fadeTransitionWidth保留原值，不能顺手一起钳制。默认值确认为SkinQuality.Auto、ShadowCastingMode.On、receiveShadows=true、MotionVectorGenerationMode.Camera、skinnedMotionVectors=true、两种ProbeUsage均BlendProbes。NaN和负零也需要保留与原比较指令一致的行为。

## 四、一次被证据拦下的选址错误

最初用于枚举构造的文本正则跨过了相邻属性，错误地把Vector3d的set_Item地址和LOD的一个setter地址配给构造函数。真实反编译显示数组下标分支/单字段setter，与构造语义不符。

随后改为按`script.json`中的精确类型、方法名`$$.ctor`、参数签名和RVA共同确认，修正为表中的0x856D2E8和0x854F458，重新分析后才写入工程。错误输出保留在工作目录的`initial-with-two-selection-errors.json`，不作为构造恢复依据。

学习要点：RVA前后相邻并不构成身份依据，尤其属性访问器、重载与构造常排列在一起。写入前必须验证方法身份和参数ABI。

## 五、测试范围与结果

测试直接读取实际工程中的字段和10个构造，用Roslyn抽取为最小测试类型，保留构造正文及构造委托关系；没有维护另一份测试版算法。

初次以C#9编译完整5个原类型，得到64个构造字段未赋值错误，以及Vector3d的4个无关out参数未赋值错误。构造恢复后，那4个未恢复方法仍阻止完整类测试，所以隔离夹具明确只取字段与构造，不修改或隐藏主工程中的out错误。

隔离验证结果：`checks=44 failures=0`。覆盖引用身份、字段赋值、默认渲染标志、负数/超界/NaN/负零输入、fade不钳制、float32扩宽。

该检查证明这些构造正文的已列行为，不能证明Vector3d全类、MeshSimplifier算法或Unity真实渲染已经可用。第四轮Unity导入会继续揭示其余真实错误。

## 七、未恢复方法的显式诊断

第四轮导入仍有部分CS0171、CS0177、CS0037错误：结构体空构造、out参数空方法以及值类型返回null。这些正文来自导出空桩，不是原算法。当前先将严格识别为这些空桩的71个方法改为抛出`NotImplementedException("RECOVERY_UNIMPLEMENTED 类型.方法 RVA=... Token=...")`，涉及29个文件。

这个改动的目的，是让编译继续分析其余程序集，并在实际场景调用到缺失实现时给出明确位置。**恢复实现计数为0**；抛异常仍是未完成状态，也不能代表该库已经可运行。没有给out参数随便填值，也没有改变已有真实构造和恢复过的方法正文。

工具只读取指定库在第四轮日志中的三类错误，使用Roslyn定位方法，确认正文为空、return default或return null后才写入。每个修改均有原文件备份、前后SHA256和方法RVA/Token。清单见[missing-method-diagnostics.json](证据/声明与构造/missing-method-diagnostics.json)。运行后凡触及这些异常，都需要继续从原生证据恢复对应方法。

## 九、主程序集声明与后续显式缺失诊断

为避免后续编译主程序集时重复出现同一类状态机声明问题，用相同Roslyn转换器处理Assembly-CSharp：670个文件发生显式接口声明变化，转换当时所有方法/accessor正文逐字相同。独立审阅确认669个文件后续哈希仍匹配；EventManager由另一个已登记阶段恢复了Init和默认参数，属于有记录的新正文恢复，不是声明工具的额外改动。

第五轮后，35个文件的94个编译阻塞空桩转为显式NotImplemented诊断；第六轮后又处理28个文件的96个空桩。它们的恢复实现计数始终为0，清单分别见missing-method-diagnostics-import5.json/import6.json。此外，4个Crowd/示例文件仅恢复IEnumerator接口声明。

另有单独取证的6项细节：

- RectClipLines64(Rect64)原ARM64只转发四个64位rect字段给基构造，无其他行为；C#已恢复`: base(rect)`，这一个转发构造可计为方法正文恢复。RectClip64本身仍未完整恢复。
- RuntimeInspector三个派生构造已核对原native确实调用base(hierarchy)，但派生字段初始化及依赖尚未整体验证，因此只恢复必需的原基构造实参，正文显式抛未恢复异常，不计完成。
- GPUICrowdRuntimeData原native先调用base(prototype)，再做类型检查、列表、回调和状态初始化。本阶段仅恢复基构造实参，其余显式抛未恢复异常，不计完成。
- Drawing两个导出的ref-null表达式，以及两个`(nint)null`指针占位不代表原代码；均改为带RVA的显式诊断，未伪造返回引用或空指针。

对应原ASM/伪C位于work/ida-framework-assets。检查中还遇到真正的跨区跳转岛：HierarchyDataRootPseudoScene在0x4653014跳到0x856E110执行一次LDR后返回0x4653018。因此不能一律把函数主区间外的跳转解释为错误；要区别自动分析误并相邻方法和真实指令岛。这次没有把带JUMPOUT的伪C当作完整实现。

这些诊断改动使编译能继续给出依赖错误，也使未来运行触及缺失方法时留下精确位置。它们不满足原游戏运行目标，后续按实际启动/玩法路径继续恢复。
