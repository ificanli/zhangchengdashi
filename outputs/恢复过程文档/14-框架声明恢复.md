# 14｜框架声明与metadata身份恢复

本阶段只恢复GFRunning的C#声明与metadata对应关系，**实现恢复计数为0**。目标是使已导出的类型、状态机和接口实现保持原身份，去掉转写错误；不会用新增空函数掩盖缺失逻辑。

## 1. 输入与约束

使用第四轮Unity编译摘要、当前GFRunning源码、原始DummyDll/GFRunning.dll和已解码global-metadata。主流程在本阶段之前已完成48文件的通用显式接口转写，并复制7个官方DOTween模块。本阶段不重复覆盖这些成果。

强制边界：不得删除业务方法，不改任何方法/accessor body，不启动另一个Unity进程。写入前备份完整原文件，写入后用独立Roslyn解析和SHA-256检查。

工具位于 `work/gf-declaration-recovery`：.NET10控制台程序，引用Roslyn、Mono.Cecil及已用于原包解析的Il2CppDumper。它读取DummyDll元数据，不执行其中方法；读取metadata表，不运行APK。

## 2. 不靠文本猜名字：状态机TypeToken

部分AsyncStateMachine/IteratorStateMachine属性出现了两类转写错误：

- 泛型状态机的typeof缺少`<>`，或嵌套状态机隐含引用外层T，导致CS0305/CS0416。
- metadata反射名字里的转义反斜杠又被编码进源码标识符，导致CS0246。例如属性指向`_005C_005B...`，实际嵌套类声明是`_005B...`。

修复步骤是从方法的原Token找到DummyDll MethodDefinition，再读取原StateMachineAttribute的TypeReference，Resolve到真实TypeDefinition，然后用该TypeToken定位当前源码中的类型声明。完全限定名和开放泛型形状来自实际声明，既不按模糊相似度选类，也不删除属性。

例如method token `0x06005753` 对应的状态机type token为`0x0200034D`，因此恢复成 `global::GameFramework.ConfigRead._005B_00B3Iz_0081_008B<>`。嵌套在泛型外层的状态机也将外层写成开放泛型，不再把T带进attribute常量。

本批修复14个状态机属性。

## 3. 枚举默认值的类型没有跟着常量恢复

TimeScale模块的多个参数被导出成：

```csharp
[Optional][DefaultParameterValue(0)] MMTimeScaleLerpModes value
```

C#要求该默认值的类型与参数枚举相符，直接把Int32对象放进属性会报CS1908。DummyDll中相应ParameterDefinition明确记录了：参数是该enum、HasConstant=true、常量是0、IsOptional=true。

因此仅把属性参数表达为 `(MMTimeScaleLerpModes)0`，保留Optional、常量值和所有方法体。委托Invoke参数也通过原delegate TypeToken定位，不按源码位置硬猜。

本批修复8个枚举默认值声明。

## 4. 用interfaceOffsets与vtable证明接口实现身份

一部分YooAsset式框架接口的方法名可读，但实现类的对应方法被混淆成无意义名字。仅凭“参数相同”“返回类型相同”不足以确定哪一个实现属于哪一个接口方法。

本批沿原metadata中的关系读取：

```text
实现类TypeDefinition
→ interfaceOffsets中的接口type index与offset
→ 接口方法slot
→ offset + slot得到实现类vtable位置
→ vtable encoded method index
→ 原实现MethodDefinition/MethodToken
→ 当前源码中带同一Token的方法
```

随后再逐项核对DummyDll中的返回类型、参数类型和泛型参数数量。只有目标唯一、来源位于本类、没有需要随之改写的直接调用时才应用；泛型接口或不明映射不猜测。

通过这条链找到了4个实现类的48个方法，恢复为对应接口的显式声明。方法原有body原样保留，没有新增转发方法或空实现。每一条记录保留接口token、方法token、interface slot、offset、实现slot及encoded vtable entry。

## 6. Priority为何没有粗暴去掉override

GameFrameModule的原property名被混淆，而getter的原方法名仍为`get_Priority`、slot=4。ILSpy因此输出了混淆属性的转发wrapper，并另列一个带同一MethodToken/RVA的get_Priority方法。11个派生类则输出为`override Priority`。RedDotModule也保留了类似的双重表达。

直接去掉override会破坏虚调用语义；直接把base属性改名Priority，又会与独立get_Priority方法产生C#访问器命名冲突。因此本批没有为了减少错误而做这两种表面修补。

一致重建需要区别“原native accessor正文”和“ILSpy额外生成的wrapper”，再统一CLR方法身份及源码属性表达。若需要调整wrapper中的调用，必须单独记录该非native生成物的处理，不能继续宣称所有body逐字节不变。本批将Priority11项作为明确未解决问题交给下一轮，没有隔离整个框架或删除调用链。

## 8. 接续阶段：43个原生构造调用链

本节接续第六轮导入后的GFRunning构造错误，前文“实现恢复计数为0”适用于前一轮声明恢复。本轮从第六轮编译摘要中的38条CS7036和5条CS1729，按原MethodToken定位43个构造函数；在40个原文件中恢复原`base(...)`参数。**本轮28个仅转发的本地构造函数已完整恢复，另外15个只恢复构造调用链，实现恢复计数仍为0。**这里的“28个完整”仅指对应构造本身的原有正文，不表示其基类、框架模块、场景或核心玩法已经恢复。

输入不是报错行号猜测：`work/gf-constructors/inventory.json`先用第六轮报错对应的历史源码取得Token，再用DummyDll确认当前类型、参数和全部基构造候选；本轮重新按Token定位当前源码，避免此前显式缺失诊断写入后行号变化。所有43项都来自原始GFRunning.dll，并逐项具有原RVA与metadata签名。

IDA9.4对43个目标逐项限定metadata确认的起止地址，再导出伪代码与ARM64汇编。本轮核验了实际函数起止地址等于请求范围、没有未解析JUMPOUT，并记录实际callsite与目标RVA。没有给基类添加任意无参构造，也没有把伪代码中的隐藏MethodInfo参数当成C#业务参数。例如多个资源加载构造在进入原基构造前把X4清零，这只是原IL2CPP隐藏方法参数；它们恢复后的C#参数仍为原有三个业务参数。

### 8.1 19个直接转发与9个被native内联的基构造

19项原native只转发到原基构造，包括资源加载、下载/解包、AudioLoopAction、AudioSingle、UIEffect等；源码恢复对应初始化器后保留空正文，因为原构造确实没有额外的派生类工作。这里的空正文有原生转发证据，与未恢复正文的空桩含义不同。

另外9项的原生代码把基构造完整内联，不能只凭“没有直接base调用”判断原构造关系。本轮补导了两个原基构造：

- OperationHandleBase，MethodToken `0x06000572`、RVA `0x71889E8`。它调用Object构造，写入provider到`0x18`，并把provider为空时的null、或provider内`0x20`的AssetInfo写入`0x10`。AllAssets/Asset/RawFile/Scene/SubAssets五个带provider的派生构造，去除指令地址及局部分支标签后，完整汇编指令与该基构造一致，因此恢复为`base(provider)`。
- AllAssets/Asset/Scene三个无参派生构造，原native调用Object构造后把继承的`0x10`和`0x18`均写为null，等价于上述原基构造的`provider == null`分支，因此恢复为`base(null)`。这个null来自原native的两项零写入；不是为编译通过临时选择默认值。
- AssetBundleLoadAssetOperationFull，MethodToken `0x060013BA`、RVA `0x7361B10`。它把bundleName、assetName、type分别写入继承字段`0x10`、`0x18`、`0x28`。AssetBundleLoadManifestOperation原构造`0x7361CA0`去除指令地址后的完整汇编与其一致，因此恢复为`base(bundleName, assetName, type)`。

独立读回脚本对六组完整汇编执行了归一后逐字比较，并检查了三个null特化构造的Object调用与两项null写入。补导两个基构造仅用于证明转发关系；本轮没有改写这两个基类尚待恢复的正文。

### 8.2 常量与Vector3参数的证据

AndroidCallback的基构造参数取自原`ScriptString`地址`0x8D7C8B8`，原值为`com.common.game.callback.GameCallbackInterface`。恢复为`AndroidJavaProxy(string)`对应的原字符串参数；callback委托的字段写入尚未在本轮实现，因此该构造保留缺失正文诊断并计0。

仅接收AssetInfo的混淆加载构造，原RVA `0x72C13A8`，实际转发为`base(null, String.Empty, assetInfo)`。其中X1由XZR赋值，X3来自原参数；X2来自`0x8CEDAE8`所指类型的`static_fields[0]`。原ScriptMetadata将该地址标记为`string_TypeInfo / System_String_c*`；原il2cpp.h的System_String_StaticFields只有首字段Empty，原dump.cs也明确记录`String.Empty`静态偏移为0，因此没有猜成任意空字符串或null。

FlyEffect、LineEffect、UIEffect的IDA伪代码均提示局部变量分配可能不准，LineEffect伪代码还把溢出至栈的Vector3部分误展示为整数参数。本轮改用汇编和ARM64 HFA规则核对：前两个Vector3使用S0至S5，进入BaseEffect时这些六个分量保持原序；Transform来自原X2，bool来自原W3并与1相与。恢复的base参数为`effectData, firstVector, secondVector, transform, flag`。FlyEffect和LineEffect另外的向量/数值字段写入仍留待正文恢复，因此二者本轮计0；UIEffect只有原base调用，本地构造计完整恢复。

对象池派生构造`0x06006AA2 / 0x727B4C4`，汇编把原第三个业务参数移动到X2，把W3与W4清零，再调用四参数ObjectBase原构造`0x06006AD6 / 0x7282604`。因此恢复为`base(name, originalThirdArgument, false, 0)`；这里的false与0都有明确寄存器赋值证据。下载构造`0x06000A3C / 0x7311508`同样有W2/W3清零证据，恢复为`base(originalDownloadInfo, 0, 0)`。

### 9.3 6个FeiShu构造的base被完整内联

六项FeiShu原构造都只直接调用System.Object构造，随后写入继承和自身字段。若只看直接调用目标，就会漏掉其原C#基构造参数。本轮补导FeiShuOrderTokenBase原构造`0x06000119 / 0x4642590`，确认它只调用Object，然后将appId、appSecret分别写入实例`0x18`、`0x20`。原metadata的基类关系和字段offset与此吻合。

原FeiShuOrderUploadLogFile构造`0x0600011D / 0x46426FC`也包含同样的两项继承字段写入，另将filePath写入`0x30`。它同时是两个发送文件派生类的原基构造，因此可以把它与派生原native的继承字段写入逐项对照。

| 原构造 | 原Token / RVA | 本轮恢复的原base参数 |
| --- | --- | --- |
| FeiShuOrderGetChatID | 0x06000108 / 0x4642550 | appId, appSecret |
| FeiShuOrderSendLogFileToChat | 0x0600010C / 0x46426BC | appId, appSecret, filePath |
| FeiShuOrderSendLogFileToRobot | 0x0600010F / 0x4642940 | appId, appSecret, filePath |
| FeiShuOrderSendLogMsgToChat | 0x06000112 / 0x4642B48 | appId, appSecret |
| FeiShuOrderSendLogTextFileToChat | 0x06000115 / 0x4642D3C | appId, appSecret |
| FeiShuOrderUploadLogFile | 0x0600011D / 0x46426FC | appId, appSecret |

发送文件到群聊的构造参数顺序为`appId, appSecret, chatId, filePath`。其原ARM64明确把第四个业务参数X4保存后写到继承的`0x30`，把第三个业务参数X3写到自身`0x38`，因此恢复的第三个base参数必须为filePath，不能直接取参数列表前三项。发送到机器人则原第三个业务参数写入`0x30`、第四个业务参数写入`0x38`，分别对应filePath和robotUrl。

独立核验脚本只把保存的汇编当作文本数据，跟踪MOV和实例STR/STP的符号参数来源，验证六组`0x18/0x20/0x30/0x38`写入及原基构造的两项继承字段写入。它不实例化或执行任何恢复的FeiShu代码。

六个构造额外的groupName、callback、chatId、robotUrl、groupId、message、text或filePath保存不在本轮构造链实现范围内，因此六项正文都保留显式缺失异常，完整实现计0；未修改其Execute、上传、发送或成功回调方法。
