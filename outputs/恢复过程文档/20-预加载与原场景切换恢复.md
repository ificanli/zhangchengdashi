# 20｜预加载、登录分支与原场景切换恢复

本阶段恢复ProcedurePreLoad与ProcedureStarGame两个原文件中的19个既有方法body，另按原metadata补回一个导出时遗漏的TryLogin方法。独立审阅未发现需要调整的原控制流；实际源码独立编译成功，17项CLR顺序和分支验证通过。

**本报告证明原Procedure调用顺序、参数和局部分支已恢复，不证明Unity中已经切换到原游戏场景或完成核心玩法。**独立审阅没有修改任何工程源码，没有启动Unity，没有执行真实SDK登录、网络请求或遥测上报。正式Unity导入与运行结果由主流程另行记录。

## 1. 原身份、输入与写入边界

主流程的输入为原DummyDll/Assembly-CSharp.dll、原script.json、已按metadata限定边界的IDA伪代码/ARM64汇编，以及当前两份原源码。写入计划与实际哈希分别位于write-plan.json、applied.json；完整写入前文件保存在项目外`work/recovery-stubs/procedures-before`。

原MethodToken和RVA保留，meta哈希与写入前记录一致。独立Roslyn读回确认19项实际body的token序列与计划一致，非目标方法文本不变。PreLoadAsync恢复成真正的C#`async void`，移除原先指向导出空状态机的AsyncStateMachine声明，让当前编译器生成实际状态机；旧导出状态机没有冒充正在执行的状态机，也没有据此额外计入实现恢复。

TryLogin的身份没有按相邻Token推测。独立Mono.Cecil直接读取原DummyDll，确认：

| 身份项 | 原metadata值 |
| --- | --- |
| MethodToken | 0x06005BBF |
| 原方法名 | `<PreLoadAsync>g__TryLogin\|0` |
| 声明类型 | ProcedurePreLoad/<>c__DisplayClass4_0 |
| 声明类型Token | 0x02000F52 |
| 方法形状 | instance、internal、void、0个业务参数 |
| 原RVA | 0x439FEE0 |
| 原闭包字段 | loginControl: LoginControl；afterLoginAction: Action |

补回的方法位于相同TypeToken的闭包类中。原native从闭包偏移0x10取LoginControl，以同一闭包的登录结果方法创建Action<bool>，再调用`Login(callback, false)`；当前实现与之对应。

## 2. 原预加载并不等待登录后再切状态

原PreLoad入口`0x439F890`的顺序是：

1. 发起PreLoadAsync。
2. 记录“预加载完成”。
3. 立即调用ChangeState<ProcedureStarGame>，使用保存的owner和空object数组。

原状态机`0x43A01BC`又明确显示：AssetsManager.Init若尚未完成，则保存awaiter并挂起；恢复之后才继续本地化预加载和登录设置。因此不能把原逻辑“修正”为等待Init或等待登录成功后再切Procedure；那会改变本次要恢复的原行为。

“预加载完成”是原字符串和原日志位置，**这条日志本身不证明资源预加载已经完成**。如果Init的await已经同步完成，后续登录发起也可能在该日志之前同步执行；这是async void的正常同步前缀行为，不是与原顺序矛盾。

状态机恢复后的实际顺序为：初始化文化和语言设置，取得AssetsManager，DontDestroyOnLoad其gameObject，await Init；随后调用本地化CustomBundlesManager.Preload().Forget，创建DataCompareMgr对象和组件，创建LoginControl及OnLoginValid回调，读取渠道，设置登录策略，清空afterLoginAction并发起TryLogin。

本地化Preload使用Forget，原链没有在此await它。afterLoginAction原值被明确写成null，当前也保持null；登录成功不额外添加新的Procedure切换门槛。

## 3. 渠道、登录校验及重试分支

渠道为空或null时不设置特殊登录标记。非空渠道先记录原字符串，再以ToLower().Contains("huawei")判断；命中时将IsDefaultTouristLogin与UseLoginCache写为false。未命中分支不假定这些字段的初始值，也不额外写入默认值。

OnLoginValid的原RVA为`0x439FB50`，三个分支按原常量恢复：

| 输入 | 标题/消息 | 按钮及回调 | 两个UI标记 |
| --- | --- | --- | --- |
| errorCode=1019 | Login_Vaild / Login_Vaild_Message | Exit_Game → AccountMsgCanvas.ExitGame | false / false |
| errorCode=3302 | Login_Vaild / 原封禁提示字符串 | Exit_Game → AccountMsgCanvas.ExitGame | true / true |
| 其他errorCode | Login_Failed / `Error Code : {0}`格式化值 | Exit_Game → AccountMsgCanvas.ExitGame | false / false |

`Login_Vaild`保留原资源键的拼写，没有按英语习惯擅自改名。GetTranslation的八项业务参数同原调用保持一致。

登录结果闭包`0x439FF74`在成功时先记录“Login 登录成功”，仅在afterLoginAction不为空时调用它。失败时展示Login_Failed / Login_Failed_Message，按钮文字为“重试”，回调指向同一个闭包的TryLogin，两个UI标记均为false。重试沿用原LoginControl，forceLogin仍为false，不创建绕过登录的临时成功分支。

该闭包伪代码在运行时数组/类型检查异常支路残留JUMPOUT；独立审阅依据汇编核对正常成功和失败分支，并保留这一限制。没有据伪代码声称原native全部异常处理已经动态验证。CLR故障测试只验证当前恢复源码的async void失败语义。

## 4. 原场景入口、退出顺序和Timer解绑

ProcedureStarGame.OnEnter原顺序为：base.OnEnter，注册ReadyExitGame事件，建立30秒循环Timer，调用SDK StartGameModel(None)，设置EnterGame=true，CheckNewDay，发起StarGame。

原StarGame入口`0x43A09D4`使用的场景请求为：

```csharp
Addressables.LoadSceneAsync("Assets/_Scene/Game.unity", LoadSceneMode.Single, true, 100);
```

这个地址来自原ScriptString `0x8D581F0`；当前没有换成恢复工具场景或测试场景。原返回handle在这里没有await或完成检查，恢复源码也保持这一行为。请求参数正确不等于场景及其资源已成功加载。

独立存在的GotoTestScene仍请求`MineGameTest`，参数为null、false、null；它没有替代生产入口。

ReadyExitGame原入口先发送MineGameExitLogic，payload为null，再使用保存的owner和空数组切到ProcedureExitGame。OnLeave则按原顺序先调用base，使用保存的GameTimer ID移除循环Timer，最后移除ReadyExitGame监听。

Timer解绑的回调需要与注册回调区别：OnEnter的原方法指针`0x8D36058`指向ReportGameTimes；OnLeave使用的是`0x8D36048`。独立查原script.json及DummyDll确认，后者为原`<OnLeave>b__9_0`，Token `0x06005BCD`、RVA `0x43A0DD0`，汇编仅一条B转发到ReportGameTimes。因此当前`time => ReportGameTimes(time)`有原生证据，不应为了delegate相等而改成注册时的同一个方法。

RemoveLoopTimer的第二个参数是移除完成回调；本报告没有把它误作需要匹配注册delegate身份的事件解绑键。ReadyExitGame事件则确实使用同一目标对象和同一命名方法进行添加/移除。

## 5. 实际源码独立编译与17项CLR验证

首先对**项目中未改动的两份实际源码**独立调用Unity自带csc，沿用主程序集rsp的引用、define、语言版本和analyzer/source generator。为只编译这两个文件，其他Assembly-CSharp伴随类型通过原DummyDll元数据引用提供；该引用只用于签名校验，未执行其中方法。结果为exitCode=0、errors=0。这不是整个主程序集或Unity正式构建的替代验收。

随后把两份实际源码逐字节复制至`work/procedure-review/fixture`，没有手写替代Procedure算法。夹具只对依赖边界提供可控实现，记录调用和参数；UniTask边界以TaskAwaiter、可控TaskCompletionSource与SynchronizationContext建立CLR级异步顺序观察。编译使用C#9，未启动Unity。

17项用例全部通过：

- Init挂起时，调用方仍先记录原日志并ChangeState，登录及本地化后续工作在Init恢复后才执行。
- Init同步完成时，登录发起位于调用方日志和切状态之前；本地化任务仍可保持pending，不被误await。
- Init失败时，async void错误由可控SynchronizationContext捕获，后续登录不执行；调用方仍保留原发起顺序。此项是CLR失败语义验证，不是native或Unity异常验收。
- null、空、普通及大写HUAWEI渠道共4项，验证只有原命中分支写两个false标记。
- 1019、3302、其他错误码共3项，验证消息、按钮、标记及ExitGame回调。
- 失败重试复用闭包和LoginControl，forceLogin保持false；成功只走原日志/可选action。
- 非空afterLoginAction在成功日志之后调用。
- StarGame进入顺序、Timer参数和原scene地址/模式/激活/优先级。
- ReadyExitGame先发送原退出消息再切原退出Procedure。
- OnLeave使用保存Timer ID、正确事件身份和原独立报告lambda；手动触发该边界回调会报告传入时间。
- GotoTestScene保持独立。
- 两Procedure的纯base生命周期转发保持。

边界中的SDK、UI和Timer实现仅用于记录。测试没有运行真实SDK调用、真实遥测、Unity场景或原战斗逻辑，也没有把mock的ChangeState当作生产FSM已经工作。
