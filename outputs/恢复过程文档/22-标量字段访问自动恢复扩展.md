## 1. 为什么能自动扩展，以及本批没有覆盖什么

旧工具已经验证了短标量访问器的字段解析、机器码 oracle、Roslyn 源码识别和实际源码读回。但是旧脚本硬编码 sample100 与旧验证目录，直接重跑会覆盖已有证据；其随机抽样也不是当前启动类型的完整清单。

本批复用 Cpp2IL 的 metadata / ARM64 解码与既有 Unicorn / 独立 CLR 验证器，在 `work/scalar-expansion/` 新建全量候选审计与源码写回工具。对精确的“读写单个原字段 + RET”指令形状，可以直接确定 C# 字段读写语义，无需让反编译器推测复杂控制流。

本批没有新增算术、转换、对象引用、静态字段、虚方法、泛型、结构体 ABI、async、构造、外部调用或任意指针表达式的恢复规则。只有原生偏移 `X0 + 常量` 的单次标量读写才会进入清单；机器码超出安全形状的成员全部排除。

## 3. 方法身份、字段身份和并行保护

每个访问器必须同时满足以下条件：

1. 原程序集为 Assembly-CSharp，原类型非泛型、非结构体、非编译生成状态机，方法为实例 scalar getter 或 setter。
2. 原 method Token、完整类型、访问器名字、RVA、返回类型、参数与 static 属性匹配当前 C# 声明。只用名字相同不能进入写回。
3. 机器码只能包含匹配宽度的 LDR / STR 或 LDRB / STRB 等单次字段访问以及 RET；bool setter 可额外有原 `AND Wn, W1, 1` 规范化。
4. getter 必须读到返回寄存器；setter 必须从对应入参寄存器写入，不能把任意临时寄存器误当作返回值或参数。
5. `X0 + offset` 必须在原类型/基类中唯一对应同类型的实例字段；显式字段再核当前源码的 field Token、类型、static 属性和实际标识。
6. 当前正文必须仍是空块或 `return default`。已存在任何真实正文、表达式属性或已生成 auto-property 均保持不动。
7. 计划保存原源码文件 SHA-256 与 .meta SHA-256；生成计划、写入前全批预检、逐文件写入前均核对源哈希。文件发生并行变化就停止，不覆盖变化。
8. 同文件替换按节点倒序执行并检查不重叠；保留原 BOM、换行、属性、访问级别和其他正文。每个文件先保存完整原始备份。

除源哈希外，最终审查还从备份重放全部计划变换，并逐字节与当前文件比较：55 文件均只含计划内的节点变化，所有 .meta 与备份相同。

## 4. 缺失 backing field 的完整条件

对导出时丢失的 `<Property>k__BackingField`，不能把非法字段标识直接写入 C#，也不能用属性调用自身制造递归。本批只在以下完整证据下把两个空壳访问器恢复成 auto-property：

- getter 和 setter 都存在，原方法身份与源码 Token / RVA 双侧匹配。
- 两侧机器码确实读写同一个原 field Token 和 offset，字段类型一致。
- 原字段与两侧方法都有 CompilerGenerated 证据。
- 原字段没有 SerializeField、SerializeReference 或其他需要单独保留的额外属性。21 字段已另作 metadata 复查，仅有 CompilerGenerated / DebuggerBrowsable。
- 源码属性没有初始化器、序列化标注或 virtual / override / abstract 行为；原 metadata 的虚属性也排除。
- 保留原 getter / setter 访问级别、Token、Address、CompilerGenerated 与其他属性标注；例如 DataManager 仍为 private setter。

这样由 C# 编译器重新生成同名私有 backing field，不增加 public 字段或猜测初始化值。

每个原生方法使用三组规范字段位模式：整数含正负/较大值，float 含正数/负数/精度边界，bool 含 true / false。模板只做字段移动，不引入算术或新转换。这些输入不是对整个类或游戏状态空间的穷举。

CLR 夹具抽取实际方法正文或完整属性声明，用独立对象承载字段，以便避开尚未恢复的其他构造和依赖；它证明当前成员的字段读写，不证明原类型的初始化、静态构造、序列化消费者、Unity 生命周期或实际游戏逻辑。原字段 offset 的正确性由 metadata 与 ARM64 两侧证据约束，不把夹具的内存布局当成 Unity 布局。
