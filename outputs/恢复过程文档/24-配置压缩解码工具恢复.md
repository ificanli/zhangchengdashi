本阶段范围仅为 `Assets/Scripts/Assembly-CSharp/ToolModule/GZipTool.cs`。没有修改 DataManager、GlobalInfo、配置文件、资源加载路径或其他所有者的业务源码。三个压缩方向的方法保持原状态，不把它们计为恢复完成。

## 1. 当前配置为什么需要这个工具

第 23 阶段的原生调用链证明，`GlobalStringToConfig<T>` 先调用 `GZipTool.DecompressFromBase64`，再调用 LitJson 的 `ToObject<List<T>>`。该方法原来直接返回 null，且 DefaultEncoding 的静态初始化丢失，因而无法把已导出的实际配置送到 JSON 消费者。

当前输入是原配置的 Base64 包装 GZip 数据。解码恢复保留原算法与异常分支，没有把配置改为明文，没有在加载器旁边增加直接 JSON 解析路径。

## 3. 文本包装层的真实行为

```text
null / empty string → string.Empty
其他 string → Convert.FromBase64String
             → DecompressCore
             → Encoding.UTF8.GetString
```

`Convert.FromBase64String` 保留原空白规则：只含空白的非空字符串可解码成零字节，随后得到空字符串；没有替换成严格拒绝空白的解析器。UTF8 使用原 Encoding.UTF8 默认 replacement fallback，没有改为遇到非法字节就抛错的编码器，也没有用 StreamReader 自动检测编码或删除 BOM。

包装层捕获 `System.Exception` 后，依次：

1. `Debug.LogError("解压失败：" + base64Data)`。
2. `Console.WriteLine(error)`。
3. `throw;` 重新抛出原异常，保留原堆栈。

日志前缀来自原 ScriptString `0x8D88400`，字符为 U+89E3 / U+538B / U+5931 / U+8D25 / U+FF1A。早期 shell 显示乱码来自默认码页；已按实际 Unicode 值核对，并未推测或重写原日志内容。

这里不能只照 Hex-Rays 的正常路径翻译。伪 C 漏掉了包装层的 EH 内容，完整 ASM 在 `0x3F80A70` 之后显示 Exception 检查、日志、Console 和 `0x3F80B04` 的 rethrow helper，恢复以此为依据。

## 4. 私有 GZip 核心、缓冲池和流生命周期

确定的 null / 零长度 byte[] 直接返回同一引用。其余输入进入 try，按以下顺序构造：

1. `MemoryStream(compressedData)`。
2. `GZipStream(inputStream, CompressionMode.Decompress)`，使用原两参数重载。
3. 输出 `MemoryStream()`。
4. `ArrayPool<byte>.Shared.Rent(81920)`。

读循环固定使用 `Read(buffer, 0, 81920)`，每次将实际 count 写入输出流。没有用租用数组的实际长度替换原 81920 常量，也没有一次 Read 后就返回。

池缓冲区在独立 finally 中执行 `Return(buffer, false)`。原 funclet `0x35C1130` 的 `0x35C11CC` 将 W2 置零，vtable slot 5 对应 ArrayPool.Return(byte[], bool)，与 clearArray=false 一致。读取和写入出错时也执行该 finally；Rent 自身失败时尚无成功租用的数组，不能错误归还。

缓冲区归还后取 output.ToArray，再按输出流 → gzip 流 → 输入流逆序 Dispose。gzip 两参数构造会拥有底层输入流，因此底层输入在 gzip Dispose 和外层 using 中可能再次收到 Dispose；保持原标准流生命周期，没有改变 leaveOpen。

外围 `catch (Exception)` **返回原 compressedData 引用**。这个旧异常契约不是严格 GZip 验证器：合法 Base64 解出的非 GZip 字节，可能在核心失败后原样返回，再被包装层按 UTF8 解码。读取、分配、归还或 Dispose 失败也受同一原 catch 约束。本批保留这个由 ASM 证明的兼容分支，没有另加明文判断、JSON 判断或加载旁路。

该 catch 也被伪 C 的正常路径隐藏。完整 ASM 明确先在 `0x3F80B60` 保存原输入到 X19，Exception 分支在 `0x3F811B0` 之后匹配 System.Exception，再跳到 `0x3F810B8`，将 X19 作为返回值。不能把这里“优化”为让所有损坏 GZip 抛错。

funclet 读取保留原始固定窗口；窗口中的后续邻接函数不会被算成本 helper。其相关片段只用于核对归还参数、buffer 引用和异常传播，不用固定窗口末尾猜函数边界。
