| 原方法 | Token | ARM64 RVA | 证实的行为 |
|---|---|---|---|
| `ToolModule.StringTool.ToInt(this string str)` | `0x060006AF` | `0x3F73A70` | Int32.TryParse，NumberStyles=167，InvariantCulture，忽略 bool 结果并返回 out 值 |
| `ToolModule.StringTool.IsNullOrEmpty(this string s, bool trimSpaces=true)` | `0x060006B7` | `0x3F75418` | null 直接 true；trimSpaces 真才 String.Trim；之后读 Length==0 |

两方法均按常规 ARM64 ABI 接收引用 / bool 并返回 int / bool；没有结构体或隐藏返回缓冲区。完整正文没有自有异常捕获或日志路径，恢复也没有增加 catch。

## 2. ToInt 使用 NumberStyles.Float，不能按名字推成默认整数解析

关键 ARM64 证据：

```text
0x3F73AAC  将 out 局部值初始化为 0
0x3F73AC0  CultureInfo.get_InvariantCulture
0x3F73AC4  将 culture 放到 X2
0x3F73AC8  X3 = out 值的地址
0x3F73ACC  W1 = 0xA7
0x3F73AD8  Int32.TryParse
0x3F73ADC  从 out 局部读 W0 并返回
```

`0xA7 = 167 = NumberStyles.Float`。该组合为 AllowLeadingWhite、AllowTrailingWhite、AllowLeadingSign、AllowDecimalPoint 和 AllowExponent；不包含 AllowThousands、AllowTrailingSign、AllowParentheses、AllowCurrencySymbol 或 AllowHexSpecifier。

实际恢复：

```csharp
int value = 0;
int.TryParse(str, NumberStyles.Float, CultureInfo.InvariantCulture, out value);
return value;
```

原代码不读取 TryParse 的 bool 返回值。成功时返回解析的 int；失败时 out 值为 0，因此 null、空字符串、格式错误、不能表示为整数的数值和溢出都返回 0。合法的字符串 `"0"` 与失败输入都得到 0，调用方不能借此区分成功状态。本批没有追加校验、日志或不同的失败值。

| 输入例子 | 结果 | 原规则的含义 |
|---|---:|---|
| `"17"`、`" +17 "` | 17 | 原风格允许前后空白与前置正负号 |
| `"3.000"` | 3 | 允许小数点，但结果必须可以表示为整数 |
| `"1e3"` | 1000 | 允许指数形式 |
| `"1.2e1"` | 12 | 指数调整后为整数 |
| `"0.1"`、`"12e-1"` | 0 | 非整数结果解析失败 |
| `"1,000"`、`"1,0"` | 0 | 没有 thousands，也不随当前区域改用逗号小数点 |
| `"2147483647"`、`"2.147483647e9"` | Int32.MaxValue | 精确保留 int 上边界 |
| `"-2147483648"`、`"-2.147483648e9"` | Int32.MinValue | 精确保留 int 下边界 |
| 相邻越界值、`"1e100000"` | 0 | 溢出失败，不抛 OverflowException |
| null、empty、非法文字 | 0 | 原 TryParse 失败契约 |

ToInt 没有先调用本工具的 Trim helper。其空白识别由 Int32.TryParse 的原风格决定，不能提前 Trim 后扩大它可接受的输入。当前 CLR 测试也明确区分了普通空白和不被数字解析器接受的 NBSP 包围输入。

## 3. IsNullOrEmpty 的 null、Trim 与默认参数

原方法先在 `0x3F7541C` 检查 null，null 不调用 Trim，直接返回 true。非 null 时，`0x3F75420` 检查 bool；真才在 `0x3F75428` 调用无参数 `String.Trim()`。最后读取原 string Length 并判断是否为 0。

实际恢复等价于原步骤：

```csharp
if (s == null)
    return true;
if (trimSpaces)
    s = s.Trim();
return s.Length == 0;
```

这里的 Trim 是标准 String.Trim，不是只去掉 ASCII 空格。trimSpaces=false 时，空字符串仍为 true，但空格、Tab、换行都属于非空内容。true 时可由标准 Trim 去掉的 Unicode 空白也参与判断；零宽空格、BOM、NUL 字符不被误当成零长度字符串。

原 metadata 将 trimSpaces 声明为 **Optional | HasDefault，默认 true**。源码签名保持 true；实际编译 IL 为 `.param [2] = bool(true)`，测试同时验证省略参数调用、反射默认值和 ExtensionAttribute。没有把调用点改为强制传 bool，也没有修改 caller 原字符串或具体路径。

这使第 21 阶段的本地路径空值判断能够取得原 bool 结果，但路径是否存在、资源是否读取成功仍由该消费链单独验证。

## 5. 单列编译诊断：ToEnum 仍未恢复

同文件另一个原导出空桩 `ToEnum<T>`，Token `0x060006B1`，正文为 `return (T)null`，且没有 class 约束。主流程在主程序集编译层确认该行产生 CS0037。

为使实际完整文件能编译，本批按单独明确授权，只把这个严格旧非法空桩改成 `NotImplementedException`，消息记录原 Token 与两个共享泛型 RVA：`0x4ED6794`（Int32Enum）和 `0x4ED68A4`（完全共享泛型）。没有给开放泛型添加某个实例的 Address Attribute，也没有增加 class/enum 约束或推测 Enum.Parse 实现。

**这项零恢复，不计入两个已恢复方法。** 当前调用 ToEnum 会明确暴露缺失实现，不能当作它已可用。其他工具方法的原正文逐项与备份比较，均保持原样。

负对照夹具只在 work 将原 ToEnum 非法空桩规范成同一个显式诊断，以便编译；被验证的 ToInt / IsNullOrEmpty 两个正文仍为恢复前的原空块/默认值，没有补逻辑。
