# 38｜存档管理器底座恢复

本阶段恢复原存档管理器的对象注册、单例生产、Data 字段、空档初始化、JSON／压缩格式与计时数据构造链。它解决“所有静态 I 仍为 null、Data getter 恒返 null”的原底座缺失，不通过 Data getter 自动创建对象，也不设置数据加载完成或登录成功标志。

授权的 **8 份原源码已写入并冻结**，全部 meta／GUID 保持不变。最终候选经过 Unity 原引用的独立 GFRunning 和主程序集编译，均 exitCode=0、errors=0；Editor **51 项**与 APK 边界 **37 项**验证通过。实际 Unity 导入、场景运行、完整存档保存与原核心玩法仍由主任务统一验收。

原平台文件／服务端存储闭包尚未恢复。因此本阶段提供明确标记的 LocalEditorStore 平台 I/O 适配，且 **非 Editor 原存储入口抛出 RECOVERY_UNIMPLEMENTED**。这不属于原 APK 文件格式或服务器存档恢复成功。

## 原泛型身份与 Data 自动属性

原 DbtSaveDataManagerBase 类型 Token `0x02000073`，T 约束自身泛型基类，TD 约束 ServerBaseData 与 new()。原 Data property Token `0x1700001F`，get／set Token `0x06000265/266`，原 backing field Token `0x0400021B`，三者均有 CompilerGenerated 证据。共享 native getter `0x6AF3D70` 与 setter `0x6AF3D78` 直接读写实例 `0x30`。

因此恢复真实自动属性，而非用返回新对象或查全局字典模拟。原静态 I 是普通 static field `0x04000219`，仍由原 OnInit 赋值，不能把它改成懒加载单例。

原 MethodInfo 调用槽也按实际封闭类型保存。例如 PlayerTimeData 的 Save 槽 `0x8CFB3E0`、Data getter 槽 `0x8CFB3E8`，PlayerCoreData 的 Save 槽 `0x8CFB260`、Data getter 槽 `0x8CFB268`。它们使用同一份共享 native 代码，但对应各自的 T／TD。没有用 `object/object` 伪对象替代真实模型。

## 注册怎样真正产生 I

原 Pool.OnInit RVA `0x71783A4` 依次重置原池状态、创建类型字典、创建后端并发出原更新／消息登记请求；随后根据原开关调用私有自动注册 RVA `0x7178538`。

自动注册的顺序已同时核对 native C 与完整 ARM64：

1. 调用原 AssemblyUtility.LoadCSharpAssembly，获取 Assembly-CSharp 的 GetTypes。
2. 筛选 IsSubclassOf(DataManagerBase) 的类型。
3. 读取真实 ModelRegister，比较 GameName 与 AppSetting.MineGameName。
4. 用 Activator.CreateInstance 创建真实模型。
5. 复制原 AutoSyn、CompressData 两个注册值。
6. 调用模型的原 OnInit，随后写入类型字典。

ModelRegister 原构造器 RVA `0x7171934`、GameName／AutoSyn／CompressData getter `0x71718FC/0x7171864/0x71719A4` 均按实际字段恢复。AssemblyUtility 则恢复原程序集名称缓存字典、Assembly.Load(name)、固定 Assembly-CSharp 加载与原错误日志。它不另行枚举所有当前程序集。

原 DbtBase.OnInit 共享 RVA `0x6AF3D80` 记录日志、登记 I、保存类型名、读取本地原始字符串，再调用 UpdataData(false)。**它只建立管理器与缓存，不创建 TD，也不调用 Load。** 后续 DataManager.LoadData／LoadAllSaveData 仍须按原顺序调用模型 Load；该编排由主任务另行恢复。

Pool.AddModel 的重复类型分支按原行为记录错误并返回传入对象，不替换已登记模型，也不重新 OnInit。GetModel<T> 找不到时警告并返回 null，不创建模型。原非泛型类型查找的缺失／null 分支存在异常细节：ARM64 确实向 `new object[1]` 的元素 1 写入，产生 IndexOutOfRangeException。本阶段保留该原失败契约，并在 fixture 独立验证；没有把反编译中的异常尾部填成正常成功分支。

Pool 原静态构造器 RVA `0x717B0B8` 写入 u=false、CanSaveLocalData=true；该恢复来自实际 STRH 0x100 原指令。它不是为测试而人为开启服务器保存。

## 原空档、JSON 与初始化顺序

原 Load 共享 RVA `0x6AF4198` 只在 Data==null 时执行：缓存为空先重新 ReadLocalData；仍为空则 `new TD()` 后执行 InitFromDefaults；有字符串则按原压缩格式解码，再 JsonConvert.DeserializeObject<TD>；最后执行 Data.Init。

GetData 共享 RVA `0x6AF42C8` 的语义不同：空字符串返回 new TD + InitFromDefaults；非空返回解码／反序列化结果，**不执行 Init，也不赋当前 Data**。LoadFormMemory 则赋入实际对象再 Init，null 保持原异常。

原 PlayerTimeData 构造器 RVA `0x4376AFC` 只创建 `Dictionary<string, TimeInfo>`，lastExitGameTime 保持默认值。真实 Newtonsoft 按 `[JsonProperty("tid")]` 与 `[JsonProperty("legt")]` 消费原字段；没有改成 MemoryPack 或未经压缩的 JSON。

损坏输入没有被当成新用户数据：无效 base64、gzip 与 JSON 保留异常；JSON 文本 `null` 在 GetData 中仍返回 null，而 Load 随后在原 Data.Init 位置失败。明确的 `{"tid":null}` 也不擅自修成新字典。空档与坏档的含义保持区分。

## 原存档专用压缩格式

此处恢复的是 `L_Tools.DataCompressTools` 存档链，和前阶段配置表解码工具不是同一条调用链。原静态构造器 Token `0x06005E0E` / RVA `0x43F9614` 设置后缀 `1234567890` 与字节 key=90。

原保存格式为：

```text
JSON UTF8 bytes
  → GZip
  → base64 string
  → UTF8 bytes 每字节 XOR (~0x5A 的低8位，即0xA5)
  → base64 + "1234567890"
```

原 DecryptString 在没有该后缀时直接返回输入，因而保留早期仅 gzip/base64 的兼容路径。原解压循环使用 32768 字节缓冲区；压缩和解压的 stream dispose／finally 语义保留。没有给无效数据添加吞异常的新回退。

编码验证使用明确字节例子 `EncryptString("ABC") == "5Ofm1234567890"`、中文 JSON 往返、旧无后缀格式、日期 Kind 与计时器字段往返；没有把不同运行时 gzip 字节逐字相等作为标准。

## 原保存门与明确的 Editor 平台边界

原 DbtBase.Save 共享 RVA `0x6AF43D4` 的条件保留为：

```csharp
!_cleared && CanSave && LoadingModule.LoadingManager.EnterHome
```

通过后先 OnBeforeSerializeForSave，再原 Newtonsoft 序列化、原压缩；结果非空才写缓存并调用 SaveLocalData。OnSave 保存当前缓存，不重新序列化修改过的 Data。Clear 幂等，第一次标记 cleared 并请求保存空字符串，之后 Save／OnSave 被原条件阻止。

LocalEditorStore 只替换平台 I/O，存取的是上述原压缩字符串。最终 Editor 写入还保留原模型 local-enable、Pool.CanSaveLocalData 与原 accountType>=10 条件；TryGame=1 等原禁止模式不写文件。它不写 CanSave、EnterHome、账号、绑定、网络或服务器完成状态。

原平台底层还包含 GamePath 的本地／服务器目录、FileManager、dotJoy 外层文件处理、额外压缩、MD5 变化检测、SDK 与版本同步等未闭合依赖。**非 Editor 的 ReadLocalData、SaveLocalData 和私有平台 writer 明确抛出 RECOVERY_UNIMPLEMENTED；它们是诊断边界，不计为完整原 I/O 实现。** 原 APK 文件包裹格式和服务器读写没有恢复完成，也没有实际访问模拟器存档。

另一个仍须恢复的真实条件是 ILoginProcedure.accountType 访问器：当前源 getter 仍是导出默认占位。原枚举 None=10、TryGame=1、OnlyLogin=2，而本阶段保留原 >=10 门，所以该外部访问器未恢复时可能继续阻止实际 Editor 写入。fixture 在受控状态下验证门的允许／禁止行为，不通过生产赋值绕过它。

后续46阶段已按原 getter／setter／cctor 补齐该访问器，并以 native 和实际输出 DLL 确认原默认 None=10。以上保留38交付时的依赖快照；该账号访问器缺口已由46解决，SDK与冲突决定等其他边界仍需各自验收。

## 后端登记及外部未知

原后端构造器 RVA `0x72B7900` 分配两份原 list、设置原 bool 和数值 3／8192。初始化 RVA `0x72BA280` 清 list，并请求登记原更新 handle 和三条消息：

- GF_HttpServerErrorCode。
- GF_HttpWebRequestError。
- GF_HttpServerSuccess。

这些请求不写登录或服务器成功标志。原 callback 消费者与 MsgDispatcher 尚未形成真实闭环，源码额外输出明确未完成 warning；它不会把“已经调用登记 API”宣称为服务器已可用。更新、消息、SDK 上报、登录访问器及原外层文件服务保持外部边界，本阶段没有继续扩展恢复整套 SDK。
