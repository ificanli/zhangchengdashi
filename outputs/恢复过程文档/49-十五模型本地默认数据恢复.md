# 49｜十五模型本地默认数据恢复

本阶段按45原 ARM64 成功加载序列追踪15个真实 TD，恢复其中已确认的纯本地构造、默认值和原 null 策略。**24 个原正文已写入14份原文件并冻结**；14份 meta／GUID 不变，288个非目标成员逐字不变，38已恢复的 PlayerTimeData 构造器及原108／新145访问器保持不变。

最终实际生产源的独立完整主程序集编译 exitCode=0、errors=0。执行原 ARM64 的46组场景，再以实际 TD 源／真实 JSON 合同比较，**931项检查、0失败**。前态源码负对照产生239处失败；将原卡牌ID1001单独突变成1006，检出1处准确差异。

这批范围是 **13个有实际载荷的TD构造器、9个非noop的本地 InitFromDefaults、PlayerCoreData.Init，以及必要的 SeasonData 子构造器**。另10个涉及配置、AB、迁移、PlayerPrefs、保存或事件的 Init 保持未恢复边界。因此本阶段不宣称45完整15个 Load 的数据内容、原核心玩法或真实 Unity 运行已验收。

## 原顺序和真实类型

原顺序直接来自45的 `native-golden.json` 中首个 `LoadAllSaveData / missingIndex=-1 / error=null`，再用原 DummyDll 每个管理器基类的第二泛型参数确定 TD：

MainCity → Card → Shop → Arena → Rank → Resource → Chest → Time → Ad → Artifact → Customization → Core → Guide → MysteryAdventure → WorldCupActivity。

原15个类型共203个字段、64个集合声明。本阶段没有因声明是集合就统一补 new；只恢复原 native 实际创建和实际修改的字段。

15个 TD 都没有自己的 static ctor。Guide、Mystery、WorldCup、Time 继承原 base.Init；Rank、Mystery、WorldCup、Time 继承原 base.InitFromDefaults。ServerBaseData 的这两个原方法是合法 noop，不能把空正文一律当成缺陷。

PlayerChestData 构造器、Card／Chest 的 Defaults 都只转发原无业务 base，本阶段保留其等价空正文，不把它们再次计入恢复数量。PlayerTimeData 构造器已经由38完成，未重复修改。

## 原默认行为中的关键细节

- Card 构造器的 battleCardID 仍为原顺序 `1001,1002,1003,1004,1005,1011,1013,1014`，没有按新配置推测替换。
- Shop 按原 ctor 建立各缓存／列表、原空字符串、两个业务 bool 与 -1 哨兵。Defaults 对指定集合执行原本的重建，而非一律“非null则保留”。
- MainCity、Arena、Resource 的指定集合在 Defaults 中仅 null 时创建；已有集合保留身份与内容。
- Ad ctor 仅把原 Stone／Crystal 两个计数置5；Defaults 才写原四个计数5及另一计数1，不把两个阶段合并。
- Artifact ctor 保留系统轮换顺序1、玩家选择顺序-1；Defaults 写原 userEquipPropID="3001"。groupA／groupB 等不是本 ctor 创建的对象仍保持原 null，后续迁移 Init 未完成。
- Customization ctor 恢复原三项本地开关及 HeadShotID="1003"。Defaults 只在 playerName 为空／空白时生成 `User` + 原数字；不覆盖已有名字，不生成或伪造 SDK 用户ID。
- 该名字算法保留原6轮，每轮分别 new System.Random 并 Next(0,9)，再乘10^i累计。不改成单个缓存Random、不补零，也不扩大到数字9。
- Core ctor 创建原经验奖励列表、SeasonData、祝福列表与战斗统计字典。SeasonData 子ctor只创建原两份赛季／周赛字典。
- Core Defaults 恢复原 moraleNum=20、isPopPacks=true，执行4次原 `Random.Range(0,100)`，结果小于80追加1，否则追加2；不清空已有列表。列表明确为null时保留原异常，并且原随机调用发生在失败前。
- Core.Init 仅在原战斗统计字典为null时建立字典；已有字典不替换。
- Guide 保留原 isFirstThroghGame=true，以及原构造器创建的三份教程／解锁集合。
- Mystery／WorldCup 只恢复各自原构造中实际存在的本地集合与常量，没有添加未分析的活动状态或奖励。

这批业务默认值均来自原 native，不是新的数值设计或为启动而随意补默认。

## 两个构造边界的补证据

PlayerArenaData.ctor RVA `0x436BFE4` 的初始伪C只有 JUMPOUT，不能据此猜 new 字段。补导出原块 `0x856E7E0` 后确认它只有一次 LDR，随后返回 `0x436C008`。原后续代码创建 List 写到实例0x10，再 tail-B 到 ServerBaseData.ctor；没有 SDK 或成功标志副作用。

Core.ctor RVA `0x4371B5C` 直接调用 SeasonData.ctor `0x436A224`，因此该子ctor纳入最小闭包。其两份真实字典对应原 allSeasonData 与 allWeeklyClashData；没有扩展恢复赛季玩法或服务器接口。

WorldCup.ctor `0x437A9E8` 的请求区间延伸到 `0x437AEFC`，其中包含随后无关的 UniTask 状态机小函数。完整 ARM64 显示实际 ctor 在 `0x437AAC0` 恢复栈后无条件 tail-B 到 base，因此可执行 ctor 范围截止 `0x437AAC4`。后续异步函数不计入该构造器的依赖、执行或恢复数量。

## 原ARM64 oracle与实际源验证

oracle 执行 APK 原 arm64 指令，未从 C# 候选反推“期望值”。场景包括16个构造（含受保护Time、原等价Chest及Season子对象），9个 Defaults 各自的新对象／JSON null／已有值三种输入，以及Core.Init三种输入，共46组。

测试边界明确分开：

- TD 的字段写入、条件、列表追加顺序、原岛跳转、原随机请求参数及异常路径由原指令执行。
- 系统集合构造、字符串和随机数作为显式边界 hooks，提供空集合语义和受控输入；不执行或验证整个系统库的内部容量／GC实现。
- 实际候选及生产源验证使用原 TD 的完整字段声明、原选中正文与原 JsonProperty，使用真实官方 Newtonsoft 和实际主程序集／GF伴随类型。只有 RNG 在独立源投影中受控，以覆盖79／80阈值和6次 Random 构造等边界。
- 未恢复的业务方法不放入源投影，不用简化 DTO 替代原 TD。该层是选中原源码的受控边界验证，不是 Unity 运行验收。

JSON 场景由真实反序列化先调用 TD 构造器，再应用明确的 null 或已有集合输入。检查包含集合内容和引用身份，能够区分“原本保留已有对象”“原本重建对象”“原本明确null后抛异常”，没有把所有 null 都修成新对象。

正对照为931项全通过。两个负对照均从相同字段／方法测试运行：原前态源码产生239处失败，单值1001→1006突变产生1处 battleCardID 精确差异，证明检查能够发现丢失正文和局部错误常量。
